# 用户文法 AST 实现的多方案比较

最新状态：本轮比较后，用户确认采用自己的文法，正式解析器已选择外层传入种类方案。见[正式采用说明](用户文法正式采用.md)。以下是保留的迁移前实验记录，比较脚本固定使用 Git 提交 `9251b89` 作为原版基线。

本轮在前两种实现的基础上，又实际实现并编译了四种方案。文法、AST 公共接口、错误检查均保持不变；各实验解析器只生成在独立构建目录，正式编译器没有替换。

## 实测结果

有效行数统一排除空行和独占一行的中文注释，包含完整解析器和各方案新增的字段、函数。不是归约函数一个局部的行数，也没有为了统计压缩原有排版。

| 实现 | 生成文件 | 有效行数 | 主要做法与代价 |
|---|---|---:|---|
| 项目原文法 | original.cpp | 319 | 原项目的实现，语言范围有差别 |
| 用户文法：首次适配 | adapted.cpp | 333 | 先建 ParamDecl，成员首项再改成 MemberDecl |
| 用户文法：新增声明信息字段 | candidate.cpp | 345 | 新增名字下标、数组部分两个字段；外层创建最终节点 |
| 用户文法：复用字段保存完整类型 | reused.cpp | 345 | 不新增字段；type 保存完整类型，名字按当前 MiniC 声明格式定位 |
| 用户文法：复用范围和节点函数 | ranged.cpp | 346 | 复用 begin/end/type 和 object()，外层从声明起点补基础类型 |
| 用户文法：合并外层创建动作 | delayed.cpp | 339 | 参数表、参数续和成员声明共用节点创建分支，仍按声明格式定位名字 |
| 用户文法：外层传入节点种类 | context.cpp | 336 | 分析栈帧新增节点种类字段，形参直接创建参数或成员节点 |

之前设想的“复用已有字段就会省代码”没有直接实现：少了字段，同时需要更多定位名字、分离数组元素类型的动作。合并外层动作能减少这部分重复，但仍没有比首次适配更短。

这轮新增方案中，外层传入节点种类的版本最短，比新增声明信息字段的版本少 9 行。首次适配仍是已验证用户实现中行数最少的版本，但不能由此证明它的理解和维护成本最低，更不能证明它是用户文法的最短实现。

## 外层传入种类如何工作

同一条规则可以出现在两种地方：

```text
函数形参 -> 形参 函数形参2
结构体成员声明 -> 形参 结构体成员声明2
```

外层已经知道自己正在处理参数还是成员，因此可以在展开产生式时把这个信息放进分析栈帧。默认是 ParamDecl；展开成员声明的右部时指定 MemberDecl。

形参完成动作直接执行 `node(declaration_kind, ...)`，一次建立正确种类的节点。分析栈中的完成动作保留这个字段；它不使用全局“当前是否在结构体中”的开关，进入和退出嵌套声明不需要额外恢复全局状态。

这样也不需要重新从源码判断名字在哪：仍用产生式右部 ID 对应的语义值。基础类型和数组处理沿用首次适配版。语法的 FIRST/FOLLOW/SELECT 和预测表不受这个字段影响；这是 AST 动作的上下文信息。

相对首次适配，该方案修改了 Frame 和 reduce()/run() 的信息传递；相对声明信息版，它没有新增 Value 字段或节点创建辅助函数。具体代码见[外层传入种类的差异](用户文法外层传入种类.diff)。

## 验证结果

七份独立 C++ 解析器均已用 MinGW C++17、`-Wall -Wextra -Wpedantic` 实际编译。本轮没有修改文法来适应某一种实现，也没有删掉数组、字面量、括号深度和 AST 高度检查。

145 个样例中，六种用户文法实现在全部样例上的 AST 和诊断代码/起始偏移完全一致。共同成功时比较的 AST 包括节点种类、名字、声明类型、孩子顺序和源码起止偏移。测试包含空/多参数、普通与结构体类型、数组作为首成员、多成员与长声明、局部嵌套结构体、成员和数组后缀、连续赋值、加减乘除结合性及原有错误样例。

与原项目文法比较：

- 94 个样例共同成功，AST 全部一致。
- 47 个样例共同拒绝，词法失败情况或诊断代码/起始偏移一致。
- 4 个样例属于原来已知的三类语言范围差异：else if、按值结构体形参、`&-a`。按值结构体形参多补了一个组合样例，所以差异样例从 3 个变成 4 个，没有增加新的差异种类。

这些是有限样例的实测结果，不是全输入等价性证明。六种用户实现的语言范围相同；用户文法本身的新增形状仍未迁移正式语义分析和 IR。

## 当前建议

如果希望节点一开始就具有最终种类，同时不引入独立声明记录与新的创建函数，外层传入种类的 336 行方案是本轮更合适的候选。它比首次适配多 3 行，代价是多一个栈帧字段及参数传递；是否值得，应该按代码是否容易理解来判断。

若只追求最少代码，已验证的首次适配仍是 333 行。节点在 AST 对外交付前统一补名字、类型、种类，本身也可以是一种合法设计；不能仅因为有一次 kind 赋值，就认定实现有问题。

两套文法及本轮各方案仍使用 LL(1) 查表，固定文法下分析时间都是 O(n)，栈的最坏空间都是 O(n)。本轮没有测量运行速度，也没有宣称哪种方案达到全局最优。
