# 用户文法与原文法的实际代码比较

运行效率属于同一数量级；本次直接实现中，原版的完整解析器略短，用户版的变量声明后续更容易复用。两版没有明显的总体复杂度差距。

本轮不是只数产生式：在独立构建目录中实际生成用户文法的预测表，改写 C++ AST 动作，分别编译两版解析器并对照结果。正式 `src/语法分析/parser.cpp` 和预测表均未修改。

## 实测数字

| 项目 | 原版 | 用户版 |
|---|---:|---:|
| 产生式 | 110 | 114 |
| 非终结符 | 49 | 55 |
| 右部符号总数 | 215 | 208 |
| 非空预测格 | 389 | 397 |
| 按项目现有稠密数组存储的预测格 | 2,107 | 2,365 |
| 完整 parser.cpp 物理行数 | 344 | 358 |
| 去掉空行和独占一行的中文注释后 | 319 | 333 |

有效代码多 14 行，约 4.4%。按当前编译器每个 int 为 4 字节计算，预测数组多 1,032 字节，约 1 KB。自动生成的表、实验脚本和测试探针都不计入解析器代码行数。

这些行数描述的是本次实现，不表示用户文法一定要多 14 行，也不是两版最短实现的证明。格式、辅助函数组织及语言范围都会影响行数；不能仅凭这一项断言哪份文法更好。

## 时间和空间复杂度

令 n 为输入的 Token 数，固定文法后，两版 LL(1) 查表分析的时间都是 O(n)，分析栈和语义值栈的最坏额外空间都是 O(n)。两版使用同一分析循环，查表、展开、匹配和完成动作的机制完全相同。

两版都沿用逆序保存列表、移动尾表和最后恢复源码顺序的策略，AST 构造没有新增反复复制整条长列表的操作。按现有高度表的哈希访问平均 O(1) 计，AST 的节点操作保持线性；若把名字和字面量文本的复制也计入，另加处理词面总字节长度的成本，两版相同。括号/树高限制和错误检查保留原样。

产生式多四条不等于运行慢四条；右部符号少七个也不能证明运行更快。本轮没有做耗时基准，因此不报告速度百分比。

## AST 动作具体改在哪里

| 函数 | 原版有效行数 | 用户版有效行数 | 原因 |
|---|---:|---:|---|
| declaration() | 24 | 19 | 成员声明移入自己的归约分支 |
| reduce() | 63 | 82 | 声明复用、语句分层和共用赋值后缀需要不同的结果交接 |
| statement() | 26 | 26 | 控制流 AST 的基本形状相同 |
| expression() | 9 | 9 | 二元运算仍采用同样的左结合连接 |
| run() | 36 | 36 | LL(1) 分析循环完全相同 |

declaration() 少五行的主要原因是把成员处理挪到了 reduce()，这部分不能算整个解析器省了五行。各函数仍按相同的排版风格计数，没有通过压成一行改变统计结果。

**变量声明逗号递归：用户版更直接。** 用户的 `变量声明后续2 -> "," ID 变量声明后续` 复用完整后续，后续中已经建立变量节点；逗号分支只需接收结果并补名字。原版的逗号分支还要重新创建变量或成员声明节点。这项复用有实际收益。

**成员声明复用形参：文法省重复，AST 需要交接。** `形参` 已产生带完整类型的 ParamDecl，成员声明需把首项改成 MemberDecl，并为逗号后的其他成员补上共同类型和声明位置。原版把变量/成员的续项创建合并在一个分支，动作层的共用反而更多。因此不能只看“复用了形参”就断言总代码更短。

**初始化与赋值共用后缀：需要分清谁创建赋值节点。** 用户版让“赋值”只返回等号右侧表达式，变量声明直接用作初值；完整表达式再创建 Assign 节点。原版把“赋值续”与其他运算尾部共用连接动作。用户版更贴近自己推导的概念，但实际需要单独的表达式分支。

**单独命名 if、while、for、返回语句：更容易对应文法，多一层结果转交。** 用户版的 `语句 -> if` 等分支直接转交结果；具体控制语句完成 AST。原版直接在语句产生式完成。这不会改变时间复杂度，但会改变动作分布。

## 实际验证及比较边界

两版使用同一词法分析器、同一公共 AST 接口、同一 AST 内存池与类型内存池，保留原来的字面量、数组长度、嵌套层数及错误位置检查，没有通过省略这些功能减少代码。

118 个样例中：

- 68 个两版都成功生成 AST，节点种类、名字、声明类型、孩子顺序及源码起止偏移全部一致。
- 47 个两版都拒绝，词法失败情况或语法诊断代码与起始偏移一致；不比较改名后的中文期望符号文本。
- 3 个属于已记录的语言范围差异：else if、按值结构体形参、`&-a`。

补充样例覆盖 1/2/8/24 个声明对象或成员，多个减法的结合顺序，以及结构体数组形参、成员类型、声明初始化和连续赋值。上述一致性是这些样例的实测结果，不是对所有输入的等价性证明。

用户版接受 else if 和按值结构体形参，且收紧 & 的操作数，因此两份语言不是完全相同的功能集。这次比较包括这些用户规则，尚未迁移语义分析和 IR，也不代表这些新增形状已经能在正式编译器执行。

对当前项目而言，没有仅为性能切换的必要。为学习和答辩，可以沿用自己理解的用户命名和声明递归方式；若采用到正式解析器，应按对应 AST 动作迁移，并单独确认上述语言范围变化。

## 复现和查看代码

先使用项目 CMake 流程构建 minic_compiler 与 lexer_probe，再运行：

```powershell
python docs/learning/compare-user-grammar.py --build-dir C:/tmp/minic-grammar-compare-20261118 --cxx D:/G++/MinGW/bin/g++.exe
```

脚本目前按 MinGW 的 `.a` 静态库和 `.exe` 可执行文件运行，构建目录必须已有本仓库当前代码生成的库。MinGW 输出路径使用英文目录；编译器路径可自行替换。

脚本在构建目录的 `user-grammar-comparison/` 生成完整 original.cpp、candidate.cpp、用户预测表、探针及对照结果。生成器中的替换点有检查，正式源码变化后若对应不上会停止，避免悄悄套用旧动作。

归档结果见[实测数据](用户文法复杂度实测.json)；便于阅读的[AST 动作差异](用户文法AST动作对照.diff)先统一两版中文命名，仅显示结构和动作变化。脚本及其生成代码只用于本次比较，不纳入正式编译器构建。
