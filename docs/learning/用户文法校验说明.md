# 用户文法整理与 LL(1) 校验

本轮把用户推导的规则整理成一套可用于 LL(1) 预测表的文法。学习目标仍是理解词法、语法、语义三阶段；正式编译器暂时沿用原文法和 AST 动作。

阅读入口：[整理版文法](用户文法整理版.bnf)；原有推导写法保存在[当前草稿](用户文法当前草稿.bnf)中。

## 已保留的设计

- 用户命名：数组定义、数组长度、函数形参2、函数实参2、表达式2等。
- 变量声明的逗号分支递归复用声明后续，分号放在结束分支。
- 成员声明复用形参中的类型、名字、数组结构，但不允许初始化。
- 声明初始化与赋值表达式共用 `赋值 -> "=" 表达式` 和 `赋值 -> ε` 两条产生式。
- if/else if 的共同前缀已提取，控制体要求代码块。
- 相邻字符串拼接已展开；取地址写作 `一元式 -> "&" 后缀式`。

## 声明整合

下列规则统一处理内外部声明，避免同一普通变量声明出现两条展开路径：

```text
外部定义 -> 基本类型 ID 外部定义后续
外部定义 -> KW_VOID ID 函数定义后续
外部定义 -> 结构体声明

局部声明 -> 基本类型 ID 变量声明后续
局部声明 -> 结构体声明

结构体声明 -> KW_STRUCT ID 结构体后续
```

外部普通类型声明允许在类型和名字后继续选择函数或变量；局部普通类型声明直接进入变量声明后续，不能定义嵌套函数。结构体声明的整条规则被外部和局部共用。

原草稿的“变量声明 -> 形参 赋值 变量声明后续2”仍保存在推导记录中。整理版把声明开头按基本类型和 struct 分流，因此不再额外保留这条重复的完整入口；初始化、逗号声明、分号结束等用户设计的后续规则不变。形参仍用于函数参数和成员声明。

不能直接并列“外部定义 -> 局部声明”与原来的“外部定义 -> 基本类型 ID 外部定义后续”：两者都会接受 `int a;`，在 KW_INT/KW_FLOAT/KW_CHAR 上发生冲突。这是整合时提取共同前缀的原因。

## 校验结果

| 项目 | 结果 |
|---|---|
| 产生式 | 114 条 |
| 非终结符 | 55 个 |
| 非空预测表格 | 397 格 |
| 预测表冲突 | 0 |
| 未定义符号、不可达规则、不能生成终结符串的规则 | 均未发现 |
| 直接或间接左递归（含可空前缀） | 均未发现 |
| LL 预测表与独立 Earley 对照 | 103 个样例判定一致 |
| 词法先行拒绝 | 另有 2 个现有联调样例含词法错误，不进入语法对照 |

这些数字验证的是完整文法和样例的识别结果，不是新文法的 C++ AST 动作已经实现。

“赋值”同时用于声明和表达式，计算得到 FIRST = {ASSIGN}，FOLLOW = {COMMA, RBRACKET, RPAREN, SEMI}。等号与 FOLLOW 不相交，所以有等号和空分支可以明确区分，复用未引入预测表冲突。

验证包含有效和无效声明、三个以上逗号成员、局部结构体、空/多个实参、尾逗号、默认参数、嵌套函数、空循环条件、表达式缺项等边界。不可修改的赋值目标、未声明名字、循环外 break 等依然可以在语法阶段建树，留给语义检查。

## 与原项目文法的差别

样例对照发现以下有意保留的设计差别：

| 写法 | 用户整理版 | 原项目文法 |
|---|---|---|
| `else if (条件) { ... }` | 语法接受 | 要求 else 后是代码块，不直接接受 else if |
| `int f(struct S s) { ... }` | 变量类型规则可生成按值结构体形参 | 只接受结构体数组形参 |
| `&-a` | 不接受，& 后须是后缀式 | 一元式层可识别，后续再拒绝非法取地址 |

用户文法能识别某种形式，不等于当前 C++ 语义分析和 IR 已支持该功能。例如按值结构体形参不能仅通过替换预测表就宣称实现完成。采用新文法前，需要核对语义支持及对应 AST 动作。

printf/scanf 不另设专用调用产生式，按 ID 与调用后缀识别。格式串、参数类型、可写入目标及取地址用途由语义阶段检查。

## 重现校验

先按项目正常 CMake 流程构建 lexer_probe，然后在项目根目录执行：

```powershell
python docs/learning/check-user-grammar.py --lexer-probe build/ninja/lexer_probe.exe
python docs/learning/check-user-grammar.py --lexer-probe build/ninja/lexer_probe.exe --check
```

脚本复用项目词法探针获取实际 Token，计算 FIRST/FOLLOW/SELECT 并生成预测表，再与独立 Earley 识别结果对照。完整集合、每条产生式的 SELECT、397 个非空预测格和样例结果见[验证数据](用户文法验证数据.json)。

语法中乘除、加减等尾部仍是右递归，AST 左结合需要在完成动作中保证。后续已完成独立 C++ 实现的[复杂度比较](用户文法复杂度比较.md)：共同成功的 68 个样例 AST 一致，用户版有效代码比原版多 14 行。正式编译器仍未替换；不能用产生式数量直接判断 C++ 代码复杂度。
